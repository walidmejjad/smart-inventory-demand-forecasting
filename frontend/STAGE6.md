## Architecture

The page reuses `useCatalog` for sales and products, existing catalog skeleton/error/feedback components, Radix-based `RecordDialog` for focus management, and Dashboard amount/date utilities. History retains backend order (ascending sale ID), follows offset/limit pagination in batches of 100 until exhausted, and searches the full loaded history. Desktop uses semantic table headers; smaller widths use cards. Item lines and total units are explicitly distinguished.

The builder maintains one cart line per selected product. Search matches name/SKU; candidate buttons show actual product price, stock, and stock status. Added and out-of-stock candidates cannot be added again. Quantities remain editable strings so blank/invalid intermediate input is handled safely, and must be whole numbers from 1 to current loaded stock (also bounded by the backend integer maximum). Removal is available before submission. Preview subtotals/totals use BigInt cents and existing symbol-free amount formatting.

The API uses the existing client/token/401 infrastructure. Actual source schemas and running `/openapi.json` were inspected before implementation. Creation sends only `items: [{product_id, quantity}]`. Prices, stock checks, SaleItems, stock deduction, and movements belong to FastAPI. On success, the builder closes, backend total appears in feedback, history/products refresh, and authoritative GET details open. Dashboard and Products fetch current data when next opened.

Detail requests are abortable and support retry and 404. Product names/SKUs resolve from loaded current products; unavailable lookups fall back to `Product #ID`. Historical unit prices/subtotals always come from the sale response. Completed-sale immutability is stated, with no edit/delete/cancel UI.

409 messages resolve product names without showing raw JSON and trigger a stock refresh while preserving the cart. Missing products and validation failures provide actionable feedback. Network/server ambiguity tells the user to inspect history before repeating a potentially completed transaction. Submission is blocked during product refresh/errors, invalid quantities, an empty cart, or an active submission.
