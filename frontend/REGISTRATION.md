## Page and API architecture

The register page shares the same branding, sidebar visual, typography, theme controls, colors, form width, spacing and footer as login. It has first/last name, email, password and confirmation fields, independently accessible show/hide controls, and a Sign in link. The original login form and authentication behavior are retained.

The actual running OpenAPI contract and source schemas were inspected. `registerAccount` submits only `first_name`, `last_name`, `email`, and `password` to `POST /api/auth/register`. Confirmation and roles are never submitted. The backend creates EMPLOYEE accounts; the UI exposes no role selector.

## Validation

- First/last name: required after trimming; maximum 100 Unicode characters each.
- Email: required, plausible email format, maximum 254 characters; trimmed before submission. Backend email validation remains authoritative.
- Password: required, 12–128 Unicode characters, not whitespace-only, and more than one distinct character, matching the backend's additional validator. Passwords are not trimmed.
- Confirmation: required and exact match.
- First invalid field receives focus; errors use `aria-invalid` and associated `aria-describedby` references.
- Names use `given-name`/`family-name`; email uses `username`; both password fields use `new-password` autocomplete.
- Enter submits; an immediate ref guard prevents duplicate submits. Fields/buttons are disabled while pending, with `aria-busy` and a live status.

409 becomes “An account with this email already exists.” Network/unavailable, backend validation and unexpected failures have safe messages without raw backend details.

## Success and session flow

Registration success immediately calls the existing AuthContext `login` with the same email/password. The existing login method stores JWT through the existing sessionStorage helper and populates the context; `GuestRoute` redirects to `/dashboard`. Authenticated visits to either `/login` or `/register` also redirect to Dashboard.

If account creation succeeds but automatic login fails, registration redirects to `/login` with an account-created confirmation. This avoids attempting registration again. Password fields are cleared after each submitted attempt and visibility resets; credentials are never written to browser storage or verification artifacts. AuthContext, token storage, session restoration and logout implementations were unchanged.
